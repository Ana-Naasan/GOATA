# Insights implementation plan

September 27, 2026. Implementation based on `main` at `3bad1a7`.
The user approved implementation and replaced the new barefoot test with Walking
review. This document defines the implementation; `HANDOFF.md` records verified
outcomes. Evaluated clinical `findings` remain empty until an assessment method
passes its evaluation gates.

## What the practitioner gets

A movable Meta UI Set **Movement review** board beside the blue replay. Each
observation explains what was estimated, shows its source view and time, and
opens the original recording. One selected card highlights the relevant region
and controls the existing replay timeline. The practitioner chooses corrections.

Two separate outputs are required:

1. **Estimated movement observations:** calculated quantities from reconstructed
   movement, clearly labelled as estimates with their limitations.
2. **Exercise assessment:** supported ELK/RTK error labels generated by an
   evaluated method. The observations above do not complete this requirement.

No chat model is needed to generate the numerical measurements or their text.
Use deterministic explanations tied to the method and measured evidence.

## How observations are generated

`Original video + timestamps → existing tracking/GVHMR → fitted joint sequence
→ geometry calculations → source-linked observations → Quest review`

Reuse the selected take's existing reconstruction. The service currently
reconstructs one take; analysing all four performances would require additional
processing. Preserve each take independently and label the scope of every result.

| Test | First quantity | Definition and scope |
|---|---|---|
| ELK, seated flank stretch | Estimated lateral torso lean | Hip midpoint to shoulder midpoint, relative to the estimated gravity direction and horizontal anatomical hip axis. Describes the fitted torso, not lumbar or vertebral motion. |
| RTK, seated torso rotation | Estimated shoulder-to-pelvis rotation | Largest absolute shortest angle between horizontal shoulder and hip axes. Describes relative fitted orientation; does not report anatomical turn direction or accumulated rotation. |
| Walking review | Estimated left/right knee flexion | 180 degrees minus the included hip–knee–ankle angle; a straight fitted leg is zero. Separate peaks for each side, without inferring symmetry or foot-contact timing. |
| Walking review | Estimated torso inclination | Unsigned angle of hip-midpoint to shoulder-midpoint relative to estimated upright. No claim about forward walking direction. |

For each quantity, retain valid source samples, a clearly defined range/extreme,
the original frame at the reported extreme, and the interval used for the summary.
An interval summary must link to that interval; a peak must link to its own frame.
Do not attach a whole-clip statistic to an invented short error interval.

### Evidence checks

- Use the validated unscaled joint samples and the exporter's original frame/time
  mapping. Display resizing, playback speed and microscope amplification cannot
  change a measurement.
- Native coordinates are right-handed and +Y up; Unity reflects Z. Test signs and
  anatomical sides explicitly. Use body-relative axes, not an assumed world-X
  patient-right direction. Document estimated gravity and orientation limitations.
- The 22-joint fitted-valid mask means finite model output. It does not prove
  that a joint was visible or correctly estimated. Available COCO17 image scores
  are uncalibrated; preserve that distinction.
- Check original frame validity, required landmark support, geometry and view.
  Define and verify measurement-quality gates before presenting reliable output.
  Numerical consistency alone cannot establish anatomical accuracy. Where quality
  is not established, show the applicable limitation or mark the metric unavailable.
- Missing joints, nonfinite numbers, zero-length axes and collapsed projections
  produce unavailable samples, never zero-valued measurements. Do not bridge gaps.
- Handle signed-angle wrapping and duplicates from inference resampling. Do not
  infer a neutral starting pose, chair contact, physical distance or foot arch
  anatomy from the existing model output.

## How genuine exercise-error findings are generated

The existing ELK candidate is an offline nearest-centroid classifier for
`elk.Error1`. It has no verified live Quest path, held-out evaluation or temporal
localisation. RTK support must be implemented separately.

1. Inspect authorized labelled KERAAL recordings, release terms, participant IDs
   and the exact annotation definitions. The upstream repository supplies example
   analysis code; it does not establish an evaluated Quest detector.
2. Start with one observable arm-position category per exercise, provisionally
   ELK Error1 (non-raised arm position) and RTK Error1 (arm elevation). Confirm
   observable inputs and sufficient reviewed labels before fixing those targets.
3. Run the same verified pose extraction and feature definitions on training and
   live input. Kinect, image landmarks and SMPL-X joints are not interchangeable.
4. Split by participant before normalization, fitting or threshold selection.
   Fit the smallest suitable classifier, reusing the existing baseline where it
   fits. Set acceptance criteria before examining the held-out results.
5. Report per-class counts, precision/recall and false positives on correct takes;
   assess fresh Quest recordings too. Save the split, preprocessing and model
   version with results. Passing this evaluation does not establish clinical validity.
6. Enable only demonstrated labels. A clip-level classifier produces clip-level
   evidence; only evaluated temporal annotations justify onset/offset claims.

Use fixed, reviewed explanations for supported labels. No invented normal-range
thresholds, confidence percentages, diagnostic claims or treatment instructions.
Until these gates pass, **Exercise assessment: not evaluated/unavailable** remains
visible. An empty result must distinguish a completed supported assessment with
no detections from an assessment that never ran.

## Display and interaction

```text
MOVABLE REVIEW BOARD                BLUE RECONSTRUCTED BODY
Patient · Test · Date               Selected region: bracket + label
Source: Front take                 One region highlighted at a time

Observations | Exercise assessment

Estimated side-bend                 FLOATING TIMELINE
[calculated value + units]          Source interval / peak marker
Front take · [source time]          Play · frame ± · speed · scrub
Estimated from reconstructed pose
[specific evidence limitation]

[View moment] [Inspect original]
Method and version under Details
```

- Show two or three compact cards, with one detail expanded. Keep the central
  body and room visible; use stock QuestDark UI Set backplates and controls.
- Matching take: selecting a card pauses and seeks to its evidence, marks the
  timeline and highlights named joints with a bracket/label as well as colour.
- Another take: pause the hologram, clear temporal highlights and open a separate
  original-video view labelled with that take. Equal elapsed times do not align
  independent performances.
- Original video opens paused at a useful readable size, at the exact source
  interval or peak. A separate **Play full recording** action supplies movement
  context without changing the measured evidence; **Return to peak** restores it.
  Magnify opens the existing paired evidence view only when accepted output exists.
- Add an optional wrist Insights shortcut. Floating buttons, controller ray and
  hand interaction remain available. Frame/next/previous actions avoid requiring
  precise slider dragging. Important limitations remain visible on the card.
- Keep unavailable, insufficient-evidence, limited-evidence, no-detection and
  processing-failure states distinct. No general pass/healthy badge.

Ship the client that accepts result 1.1 before the service emits it. Capture and
replay schema versions need not change. Keep the same authenticated service and
storage; no new Flask server, queue framework or LLM service is required.

Analysis, contract integration and Quest presentation can proceed in parallel
once the result shape and metric meanings are agreed. Use tests before nontrivial
logic, then Python/C#/security review and a real device run.
